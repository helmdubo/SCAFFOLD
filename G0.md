# 0. Executive Summary

Scaffold Core is an immutable B-rep-inspired interpretation pipeline for topology-aware structural UV alignment.

It does not attempt to become a CAD kernel. It borrows B-rep discipline — topology/geometry separation, oriented edge-use, shells, loops, adjacency graphs, feature recognition — and applies it to a polygonal Blender mesh workflow.

Scaffold Core builds a read-only **Topology Snapshot** from a source mesh, attaches derived **Geometry Facts**, derives **Relation Graphs** such as adjacency, alignment, continuation and world semantics, recognizes higher-level **Feature Candidates**, resolves them into **Feature Instances**, and runs **Runtime/Solve** steps such as skeleton solve, pin policy and UV transfer.

Scaffold owns interpretation.  
Blender owns mesh editing.

Recommended Blender add-on metadata:

```python
bl_info = {
    "name": "Scaffold",
    "author": "...",
    "version": (0, 1, 0),
    "blender": (4, 0, 0),
    "category": "UV",
    "description": "Structural UV for architectural meshes",
    "location": "UV Editor > Sidebar > Scaffold",
}
```

`category = "UV"` is intentional. The primary workflow lives in UV space.

The core package is:

```text
scaffold_core/
```

The add-on wrapper may later live in:

```text
scaffold/
```

# 1. Core Design Goal

Remove old hard-coded assumptions:

```text
old:
  WALL / FLOOR / SLOPE as primary patch types
  H_FRAME / V_FRAME as primary chain roles
  local patch basis as early truth
  solve logic mixed with recognition logic
  ContinuationEdge ad-hoc alongside Chain

new:
  geometry facts are raw, uninterpreted
  topology is explicit, oriented, immutable
  PatchChain is the final patch-local boundary edge source of truth
  AlignmentClass derives axis-like structure from PatchChain directional evidence
  WorldOrientation is a parallel semantic overlay
  features are graph-pattern interpretations with evidence
  runtime roles are late, derived, and task-specific
  continuation is a first-class Layer 3 relation
```

Two architectural cycles are explicitly forbidden:

```text
forbidden:
  skeleton solve → determines axes
  world orientation → determines alignment
```

Instead:

```text
Layer 2:
  raw geometry directions

Layer 3:
  AlignmentClass and PatchAxes are derived before solve

Layer 5:
  skeleton solve consumes AlignmentClass / PatchAxes and computes coordinates
```

And:

```text
WorldOrientation is a deferred parallel semantic overlay.
WorldOrientation does not depend on skeleton solve.
AlignmentClass and PatchAxes must not use WORLD_UP or WorldOrientation labels.
WorldOrientation must not feed back into Layer 1 topology, PatchChain identity,
AlignmentClass grouping or PatchAxes selection.
```

A world vertical exists today only as a user option of the user-filter
stage (pass 3, DD-55). It is not WorldOrientation. It lives only in that
stage, feeds nothing into Layers 1-4 (AlignmentClass and PatchAxes do not
see it) and reaches Layer 5 only as SeamDirectives, which say whether a
seam is split or joined. Both forbidden cycles above stay forbidden.

# 2. Layer Overview

```text
Layer 0 — Source Mesh Snapshot
Layer 1 — Immutable Topology Snapshot
Layer 2 — Geometry Facts
Layer 3 — Derived Relations
Layer 4 — Feature Grammar
User filters — options of the user (pass 3; not a layer, DD-55)
Layer 5 — Runtime / Solve
```

Layer 3 is frozen after Pass 1. Layer 4 communicates with Layer 5 only through explicit `FeatureConstraint` objects.

The user-filter stage (`scaffold_core/user_filters/`, DD-55) runs after
Layer 4 and before Layer 5. It reads Layers 1-4 and writes nothing into
them. It communicates with Layer 5 only through explicit `SeamDirective`
objects. With no user option set it emits nothing.

A Layer 0 source face may carry the raw Blender Face Strength mark (WEAK,
MEDIUM or STRONG), read from the FACE-domain int attribute
`__mod_weightednormals_faceweight` where it exists (in Edit Mode the
attribute data reads as empty, so the values are read from the edit
BMesh face layer of that name); a face without the
attribute, or with a value other than Blender's three, has none. The mark
states what Blender stored, not what the face is. It does not change
segmentation (G1 stays seam-only). Its one reader is the Layer 4 bevel
rule (DD-54).

# 3. G1 Patch Segmentation and Shell Policy

G1 patch segmentation uses selected-face flood fill.

A source edge blocks Patch flood fill and becomes a Patch boundary if:

```text
- it is a mesh/selection border;
- it is non-manifold in selected scope;
- it has an explicit Scaffold boundary mark;
- it has a Blender UV Seam.
```

Blender Sharp is **not** a default Patch boundary source in G1.

A future optional command/flag may support:

```text
make seams by sharps
```

That future option should convert sharp information into seam/boundary input before segmentation. It must not make Sharp a hidden default segmentation source.

Material boundaries, normal-angle thresholds and existing UV island boundaries are also not default G1 segmentation sources.

G1 shell detection uses edge-connected components of selected faces.

Shell connectivity ignores Patch segmentation boundaries: seams and explicit boundary marks can split Patches but do not split Shells.

Vertex-only contact does not connect Shells.

Non-manifold edge connectivity keeps faces in the same Shell candidate, but emits a degraded non-manifold diagnostic.

Layer 1 boundary construction follows this intended pipeline:

```text
1. Flood fill selected faces until boundary edges.
2. Build Patch boundaries and raw boundary cycles.
3. For every boundary edge, classify neighbor context:
   - self patch neighbor / seam-self;
   - other patch neighbor;
   - no patch neighbor / open boundary;
   - non-manifold.
4. Build draft boundary runs internally.
5. Redefine/coalesce/split draft runs according to policy.
6. Materialize final BoundaryLoop with final PatchChains.
7. Downstream systems use final PatchChains.
```

Final PatchChain may be the same as the draft run, or may be split/coalesced.
Do not introduce an extra public span or effective-chain source-of-truth layer.
If helper spans/runs are needed during construction, they stay private/internal.

Canonical cylinder sanity check:

```text
Cylinder tube without caps + one seam cut:
  Patch count: 1
  BoundaryLoop count: 1 OUTER
  Chain count: 3
  PatchChain count: 4
  LoopCorner count: 4
  ScaffoldNode count: 2
  ScaffoldEdge count: 4
  SELF_SEAM ScaffoldJunction count: 2

PatchChains:
  1. seam side A
  2. cap/border ring A
  3. seam side B
  4. cap/border ring B

LocalFaceFanGeometryFacts:
  many, not 2
  local normal evidence, not scaffold graph nodes

ScaffoldNode:
  graph-level evidence node assembled from loop corners and endpoint evidence;
  seam-side materialized Vertex occurrences may group by SourceVertexId.

ScaffoldJunction:
  ordinary ScaffoldNodes remain unclassified unless a ScaffoldJunction
  classifier emits a record. SELF_SEAM classifies the 2 seam endpoint
  ScaffoldNodes in this fixture after ScaffoldGraph construction.

Future ScaffoldCircuit:
  likely 2 cap/border circuits
```

# 4. Design Decisions Register

## DD-01 — Topology is immutable snapshot
Scaffold Core does not mutate topology in place.

## DD-02 — PatchChain is mandatory
All oriented boundary use is represented through PatchChain.

## DD-03 — Topology and geometry are separate
Layer 1 stores incidence/orientation. Layer 2 stores measured geometry.

## DD-04 — H/V is not a primary stored role
H/V-like labels are derived runtime/debug labels.

## DD-05 — WALL/FLOOR/SLOPE is not a primary patch type
World-facing semantics are derived WorldOrientation facts. The HORIZONTAL /
VERTICAL class of the user-filter stage (DD-55) is the verdict of a user
filter inside that stage, not a patch type.

## DD-06 — Relations are derived caches with provenance
Relations store confidence, evidence, source and snapshot context.

## DD-07 — Alignment membership is per PatchChain
A Chain may have multiple PatchChains with different AlignmentClass memberships.

## DD-08 — Patch axes are derived from AlignmentClasses
PatchAxes is Layer 3 classification, not solve output.

## DD-09 — Continuation is a Layer 3 relation
Old ContinuationEdge becomes ChainContinuationRelation.

## DD-10 — Dihedral is a PatchAdjacency relation
Signed dihedral references patch pair, shared Chain and both PatchChains.

## DD-11 — WorldOrientation is a derived relation namespace
SurfaceRole, WorldEdgeKind and WorldCornerKind are derived semantics.
WorldOrientation is not implemented. The world vertical of the user-filter
stage (DD-55) is a user option of that stage, not WorldOrientation, and
creates none of these records.

## DD-12 — Base WorldOrientation does not depend on Runtime/Solve
Solve output must not redefine world semantics. This still holds: the
user-filter stage runs before Layer 5 and reads no solve output.

## DD-13 — Alignment and PatchAxes do not use WorldOrientation
AlignmentClass and PatchAxes consume patch-local directional evidence only.
They must not use WORLD_UP vector bias, SurfaceRole labels or WorldOrientation
labels. This still holds: the world vertical of the user-filter stage
(DD-55) feeds nothing into Layers 1-4.

## DD-14 — Runtime solve consumes lower layers only
Runtime solve must not discover or mutate topology, geometry or base relations.
It also consumes the user-filter stage (DD-55), and only its SeamDirectives.

## DD-15 — Feature recognition returns candidates, not decisions
Rules produce FeatureCandidates. Resolver produces FeatureInstances.

## DD-16 — Full rebuild is preferred in v1
Correctness and debuggability beat incremental complexity.

## DD-17 — User overrides are inputs, not topology mutations
Overrides affect rebuild interpretation.

## DD-18 — Skeleton solve supports optional FeatureConstraints
FeatureConstraints are the Layer 4 → Layer 5 bridge. SeamDirectives of the
user-filter stage (DD-55) are a separate input of Layer 5 island assembly;
they carry no feature.

## DD-19 — Two-pass maximum in v1
No iterative feature/solve convergence loop.

## DD-20 — Suppressed candidates are retained
Suppressed/rejected/weak candidates are inspectable diagnostics.

## DD-21 — Detail generation is external
Detail/decal/wear systems consume Scaffold APIs.

## DD-22 — SEAM_SELF is first-class
Two PatchChains of one Chain in one Patch is supported.

## DD-23 — Architecture allows N AlignmentClasses per patch; v1 resolves at most two
Non-orthogonal/curved/N-family cases are future work.

## DD-24 — Direction clustering is conservative in v1
Straight-like PatchChains only, chord direction only, fixed tolerance.

## DD-25 — Layer 3 is frozen after Pass 1
Pass 2 may consume Layer 3 but must not write to it.

## DD-26 — FeatureConstraint is first-class
FeatureConstraint is the only channel from accepted features into solve.
The user-filter stage (DD-55) is not a feature: it reaches the solve only
through SeamDirectives.

## DD-29 — Chain coalescing is staged

Layer 1 materializes final PatchChains from raw boundary elements.

Raw boundary sides, atomic source edges, draft boundary runs and raw boundary
cycles are builder internals. They are not public model entities.

Boundary coalescing uses topology/materialization context only:
- boundary run kind;
- Patch context;
- seam/cut side;
- neighbour context;
- loop materialization.

Border runs may coalesce into ordered Chains when materialization policy
identifies them as one final PatchChain.

Reason:
Cylinder tube without caps + one seam cut showed that edge-atomic border Chains
prevent correct materialized BoundaryLoop construction. Border ring runs must
be allowed to coalesce into final PatchChains.

Geometry may later describe or classify a final PatchChain, but it must not
create a competing public PatchChain identity.

## DD-30 — Chain refinement does not change Layer 1 Chain identity

Layer 1 Chain identity is decided by topology coalescing only.

Geometry-driven Chain refinement, when introduced, lives in Layer 3 and
must be computed before AlignmentClass consumes Chain-like entities.

Refinement may produce derived sub-chain entities or alignment-level
groupings that AlignmentClass consumes. It must not rewrite, split, or
re-id existing Layer 1 Chain records after Pass 0.

This preserves stable Chain ids for downstream references and keeps
geometry-driven decisions inside Layer 3.

Directional runs are chosen per PatchChain use (plan Slice W Stage B,
user-approved 2026-11-13). A zigzag Chain keeps its single chord-directed
run only for a use where the whole Chain is one SURFACE_LINE piece on that
use's side (DD-48); every other use gets the runs split at direction
changes. The two uses of one Chain may therefore carry different runs. A
Chain whose split is a single run, and a monotone-turning arc, are not
affected.

## DD-31 — PatchChain endpoint relations are local and axis-free

## DD-33 — ScaffoldGraph is derived from endpoint relations and LoopCorners

## DD-35 — LoopCorner is patch-local; ScaffoldJunction is graph-level

LoopCorner is the local transition between adjacent PatchChains inside one
BoundaryLoop. A LoopCorner may feed ScaffoldNode evidence. It becomes a

Implemented ScaffoldJunctionKind vocabulary includes:
- SELF_SEAM: two incident final PatchChains share the same ChainId and same
  PatchId, representing the supported SEAM_SELF case.
- CROSS_PATCH: an existing ScaffoldNode's incident final ScaffoldEdges
  reference more than one distinct PatchId.

Future ScaffoldJunctionKind vocabulary beyond SELF_SEAM/CROSS_PATCH includes:
- BRANCH;
- TERMINUS or BORDER_TERMINUS;
- AMBIGUOUS or DEGRADED when describing evidence quality.

Ordinary ScaffoldNodes remain unclassified unless a ScaffoldJunction classifier
emits a record.

## DD-36 — LocalFaceFan is geometry evidence, not graph topology

LocalFaceFanGeometryFacts provides local normals for endpoint evidence. It is
not a ScaffoldNode and not a graph entity.

## DD-37 — Seam cuts may materialize duplicate topology Vertex occurrences

A seam cut may materialize multiple topology Vertex occurrences for one source
vertex.

One source vertex can appear on different sides of a materialized BoundaryLoop
or seam cut. These occurrences may receive distinct topology VertexIds while
retaining provenance to the same source vertex.

Reason:
Materialized UV-cut topology needs separate loop-side occurrences for the same
source vertex. This is required for correct BoundaryLoop traversal, PatchChain
construction, LoopCorner construction and ScaffoldNode grouping.

Implications:
- VertexId equality is topology-occurrence equality, not source-vertex equality.
- SourceVertexId equality is provenance equality.
- Public queries that need source-space grouping must explicitly group by
  SourceVertexId or structural provenance.
- ScaffoldNode construction may aggregate multiple materialized Vertex
  occurrences into one graph node.

## DD-39 - ScaffoldNodeIncidentEdgeRelation v1 is all-pairs evidence

Implemented ScaffoldNodeIncidentEdgeRelation v1 is a complete unordered all-pairs
Layer 3 relation over incident ScaffoldEdge endpoint occurrences at one
existing ScaffoldNode. For n incident edge-end occurrences at one ScaffoldNode,
v1 emits C(n,2) relations.

Emission is graph-structural. Missing PatchChainEndpointSample or
PatchChainEndpointRelation evidence must not cause an edge-end pair to
disappear. When endpoint evidence is missing, the pair remains present and is
classified with missing or degraded evidence quality.

Classification is evidence-backed. It may use tangent direction evidence,
owner normal evidence, direction_dot, normal_dot, endpoint sample ids,
PatchChainEndpointRelation id when available, confidence and evidence quality.
It is evidence only. It must not select trace paths, circuits, rails,
continuations, UV behavior or runtime behavior.

Implemented v1 relation kinds:
- STRAIGHT_CONTINUATION_CANDIDATE: opposite tangent/chord evidence;
  compatible owner-normal proof may be absent or weak.
- SURFACE_CONTINUATION_CANDIDATE: continuation candidate with compatible owner
  normals for opposite-tangent or straight-ish surface continuation.
- CROSS_SURFACE_CONNECTOR: tangent may align or connect, but owner normals
  diverge strongly.
- ORTHOGONAL_CORNER: tangent evidence is orthogonal.
- OBLIQUE_CONNECTOR: tangent evidence is neither collinear nor orthogonal.
- SAME_RAY_AMBIGUOUS: endpoint tangents point in the same ray direction away
  from the node.
- MISSING_ENDPOINT_EVIDENCE: the edge-end pair exists but endpoint
  sample/relation evidence is absent.
- DEGRADED: tangent, normal, confidence or evidence is zero, unknown or
  collapsed.

Implemented relation kind:
- SURFACE_SLIDING_CONTINUATION_CANDIDATE: node-local relation between two
  existing ScaffoldEdge endpoint occurrences whose local tangent/chord
  classification may otherwise look orthogonal or same-ray, but explicit
  same-side-surface evidence plus compatible local owner normals support
  continuation along the same curved or side surface. It is not a trace path
  choice, not a selected next edge, not a rail/circuit decision and not a UV
  direction.

SURFACE_SLIDING_CONTINUATION_CANDIDATE requires local owner-normal evidence,
compatible local owner normals and explicit same-side-surface evidence.
Current SideSurfaceContinuityEvidence v1 is consumed as this explicit
same-side-surface evidence source and includes the direction/flow-family
compatibility gate before this evidence may promote a pair to
SURFACE_SLIDING_CONTINUATION_CANDIDATE. Same patch, same loop,
END -> START adjacency and compatible local normals are not sufficient by
themselves under v1. Missing, degraded or direction-family-incompatible evidence
must not produce this kind under v1.
SharedChainPatchChainRelation alone must not produce this kind. Cross-patch
cap, corner and shared-boundary cases must remain non-propagating unless
same-side-surface and direction/flow-family evidence is explicit and safe.

ScaffoldNodeIncidentEdgeRelation v1 must not change ScaffoldNode grouping,
ScaffoldEdge identity, PatchChain identity, Chain identity, Vertex identity or
BoundaryLoop identity. It must not use H/V, U/V, WORLD_UP, WorldOrientation,
Feature, API, UI, runtime solve or UV transfer.

Examples:
- Tube without caps split by multiple seam chains: top border PatchChains may
  become SURFACE_SLIDING_CONTINUATION_CANDIDATE through seam nodes when
  explicit same-side-surface evidence, compatible local owner normals and
  compatible direction/flow-family evidence prove curved side-surface
  continuation. The expected continuity result is two side families rather than
  four singleton side boundary edges.
- Tube with cap patch: side-to-cap PatchChains may be shared/cross-patch
  neighbors, but they are not side-surface continuation when owner normals
  diverge.
- Folded 90 seam, cube-like corner and cap-cross-surface cases remain
  non-propagating unless explicit same-side-surface evidence is safe.
- Local D:\cylinder.blend is an exploratory smoke fixture, not the canonical
  synthetic fixture for this contract.

It is not a trace, path choice, rail, circuit, UV direction, runtime behavior

## DD-43 — ConnectedDirectionFamily v0 is connectivity-propagated direction-family evidence

Approved ConnectedDirectionFamily v0 is a Layer 3 derived evidence view over
PatchChainDirectionalEvidence and ScaffoldGraph connectivity. It groups
directional evidence into direction families by propagation along topology,
not by world-direction comparison.

Seeds and propagation:
- seeds are non-degenerate PatchChainDirectionalEvidence records;
- membership propagates only along ScaffoldGraph connectivity
  (ScaffoldNode incidence and SharedChainPatchChainRelation);
- evidence in disconnected Shells must never share a family
  (canonical negative: detached_parallel_walls);
- cross-patch transport rotates the carried direction around the shared
  chain by the signed dihedral (parallel transport). Dihedral modulates
  HOW a direction transports, never WHETHER it transports: there is no
  dihedral threshold; user seams already encode cut intent;
- SHARED_CHAIN crossings transport only across a straight hinge: both
  PatchChains of the shared Chain carry exactly one directional run. A
  curved multi-run Chain has no single rotation axis and does not
  transport;
- a family visits each patch at most once as one continuous in-patch
  segment. In-patch geodesic crossings form segments first, SHARED_CHAIN
  merges precede node merges, and a merge that would put two separate
  segments of one patch into one family is blocked. Opposite sides of a
  patch never share a family;
- a node crossing records the hinge Chain that passes through its node;
  two patches may share several Chains;
- a node crossing never folds back: after transport about its hinge, the
  two runs leave the node in opposite directions. Runs that leave it the
  same way (a patch wrapping around a corner node) do not cross. The run
  end at the node is the end on the node vertex.

Transport gates must distinguish junction geometry, consistent with the
two-seam-tube / tube-with-cap fixture pair:
- same-chain crossings (seam flow, cap rims) cross a locally flat
  junction: diverging owner normals disprove the flow;
- different-chain node crossings (ring flow around curved surfaces)
  legitimately have diverging owner normals and must not be
  normal-gated; they gate on transported-direction compatibility and
  non-degraded endpoint evidence.

Canonical fixture expectations:
- detached_parallel_walls: the two walls never share a family;
- l_corridor_tunnel_seamed_folds: one width (profile) family across floor,
  wall and ceiling; one length rail per fold line (floor+wall,
  wall+ceiling);
- beveled_wall_corner: one horizontal family across wall A, chamfer and
  wall B; one vertical rail per fold line (wall A+chamfer, chamfer+wall
  B);
- tube_with_cap: cap and side families stay separate;
- cylinder_tube two-seam variant: top ring family and bottom ring family
  across both side patches;
- reflex_corner (a wall hinged into the notch of an L-shaped wall): its
  bottom and the notch bottom stay separate families; the two tops share
  one family.

Non-goals and restrictions:
- v0 is evidence only: it must not choose traces, rails, circuits,
  continuations, UV direction or solve behavior;
- v0 must not change ScaffoldContinuityComponent propagation,
  ScaffoldNode/ScaffoldEdge identity or any Layer 1 identity;
- it must not use H/V, U/V, WORLD_UP, WorldOrientation, Feature, API,
  UI or runtime semantics;
- AlignmentClass remains in place; existing consumers stay on
  AlignmentClass until a later approved slice migrates them. New
  consumers should prefer ConnectedDirectionFamily.

## DD-45 — ConnectedDirectionFamily v1: occurrence-aware geodesic in-patch continuation

Approved ConnectedDirectionFamily v1 extends DD-43 with in-patch
continuation:

- two runs meeting at a junction (ScaffoldNode or RunEndpointJunction)
  continue one family IN THE OWNING PATCH-USE VIEW iff the interior
  angle sum of the owning patch's faces at that specific materialized
  vertex occurrence (DD-37: seam-side duplicates have separate fans) is
  within GEODESIC_STRAIGHT_TOLERANCE of pi. The angle alone decides:
  endpoint roles and the vertex order of source edges do not;
- the angle source is per-occurrence patch-side face-fan data (Layer 2
  / LocalFaceFanGeometryFacts); full source-vertex angle sums and world
  directions are forbidden inputs;
- family membership is per PatchChain-use (reaffirms DD-07): one Chain
  may be a straight rail in one patch view and a cornered perimeter in
  the adjacent patch view;
- SEAM_SELF chains and their endpoint occurrences never continue; a
  band's top and bottom rims are distinct families (no leak through
  seam endpoints);
- canonical fixture: extruded_cross (side band one patch + one seam,
  caps separate patches): band view top rim = one family, bottom rim =
  a different single family; cap views stay corner-split; true 90-degree
  quad-wall corners never merge;
- v1 remains evidence only under all DD-43 restrictions.

Origin: the rule formalizes the artist's visual verdicts (rim
wholeness, cap perimeter, seam cut) from the Overlay v2/v3 prototype,
which this core contract supersedes.

## DD-46 — ScaffoldTrace v1 is ordered graph evidence, not topology identity

Implemented ScaffoldTrace v1 (plan Slices J and O, user-approved) is a Layer 3
derived evidence view, one per ConnectedDirectionFamily, over existing graph
atoms: ScaffoldNode, RunEndpointJunction, PatchChainDirectionalEvidence and
the family's crossing records.

- it orders the family's members through trace nodes by stations. The two
  uses of one hinge Chain, joined by a SHARED_CHAIN crossing, cover the same
  source edges and form one station: they are listed together and occupy a
  single step between two trace nodes, never two consecutive steps. Every
  other crossing links two stations at its trace node (a ScaffoldNode, or a
  RunEndpointJunction inside a coalesced Chain). The trace names its stations,
  so no consumer regroups the uses of a hinge itself;
- each member records its directional evidence id, patch and patch-chain id,
  start/end trace node ids, the vertex occurrences of its endpoint samples
  (by sample role, which follows the PatchChain traversal, not the trace
  direction), the crossing to the previous and next member, and
  confidence; the trace records branch and loop ambiguity and its
  diagnostics;
- evidence only: it must not mutate or replace Layer 1 Vertex, Chain,
  PatchChain or BoundaryLoop identity, Layer 3 ScaffoldNode or ScaffoldEdge
  identity, or family membership. It is not UV, pins, feature grammar,
  packing, texel policy, H/V, WORLD_UP, wall/floor labeling, runtime solve
  behavior or a user-visible edit operation.

## DD-47 — ScaffoldRail v1 is a direction-stable ScaffoldTrace

Implemented ScaffoldRail v1 is a ScaffoldTrace whose station order carries a
transported orientation sign per member (+1 along the rail, -1 against it, 0
unknown), suitable for consumption as a conditional axis by Layer 5.

- it carries ordered members and stations (in a consumable rail station i is
  the step between trace nodes i and i + 1; a branched or looped rail lists
  its stations by station id), ordered trace nodes, first and last trace
  node, a closed-loop flag (the stations form one cycle), signs, crossing
  records, branch records, loop ambiguity records, confidence and
  diagnostics;
- signs come from the trace nodes of the links before and after each station;
  a rail of one station orients its uses against its first member. They are
  never taken from world direction comparison or a runtime greedy walk;
- a rail is consumable by Layer 5 only when it has more than one member, no
  branch record, no closed loop, no diagnostics and a nonzero sign on every
  member;
- loops: a closed loop is not a linear rail. It opens only where a
  structural cut the rail builder does not own (the seams an island leaves
  cut, a split seam) already opens it; the rail builder never picks a
  start;
- branches: a station with more than two links, or a trace node touched by
  more than two stations, is a branch record; a path that comes back to a
  node it passed is not a line. Branches stay explicit until a Layer 4
  feature rule or an approved Layer 3 continuation contract resolves them;
- cut view: a consumer that owns a structural cut (the members it keeps and
  the hinge Chains its cut keeps joined, for example one island's runs and
  stitched seams) may ask Layer 3 to cut a family's rail. A crossing survives
  when both members are kept and it stays inside one patch or passes a kept
  Chain; each connected piece is ordered through its stations like a whole
  rail and names its stations. A loop opens exactly where the cut opens it;
  a branch, or a loop the cut leaves closed, stays unordered with a
  diagnostic. The cut view is computed on demand and is not stored in
  RelationSnapshot;
- consumer rule: Layer 5 consumes rails through the cut view of each island
  and may check them against its own island lines and frame as validation
  outputs. It must not reconstruct missing or ambiguous rail order, loop
  signs or branch choices by local BFS, greedy traversal, lexical ordering,
  world-direction comparison or ad-hoc sign propagation; it diagnoses and
  degrades instead;
- Layer 5 takes its island lines from the cut view. An island without a
  rigid unfolded frame takes its in-line run signs from its ordered
  island rails; a run on an unordered island rail stays unsigned with a
  diagnostic and adds no length equation, but keeps its axis role. Order
  and signs inside a rail come only from the rails; the axis bipartition
  of such an island and the relative orientation of different rails
  (which flips whole lines, never one run) stay with Layer 5. Both read
  RunCornerRelation RIGHT corners (DD-49) and bridged right corners
  (DD-52): the bipartition takes orthogonality from them, the
  orientation follows the corner turn law (DD-51). Neither compares raw
  3D directions. A line these corners never reach from the island's
  longest line stays OBLIQUE with a diagnostic naming it. A line that two corners
  orient differently loses its signs with a diagnostic; a signed axis line
  that the corners do not tie to the island's longest line keeps its rail
  signs and is reported;
- a Layer 5 island is a quilt (DD-55). The hinge Chains its cut keeps
  joined are the seams its tree stitched, including seams a user filter
  joins; every other seam, including a seam a user filter splits, is in
  the UV cut set and opens the island's rails there;
- canonical fixtures: two-seam cylinder tube (both rim rings stay closed
  loop rails; the island cut opens each at the seam the island leaves cut);
  artist multiseam cylinder (both rims open into ordered island rails);
  l_corridor_tunnel_seamed_folds (open consumable length rails);
  beveled_wall_corner and t_vertex_wall (the two uses of a hinge are one
  station); extruded_cross (top and bottom rims are distinct rails);
  tube_with_cap (cap and side rails stay separate); t_vertex_wall with its
  right hinge cut (a branch at w1);
- ScaffoldRail remains Layer 3 evidence: it must not choose UV coordinates,
  pins, island packing, texel scale, feature constraints or Blender
  operations.

## DD-48 — PatchChain shape is judged per use on its own patch surface

Implemented v0 (plan Slice W, Stages A and B). Background, stages and
measurements: `docs/architecture/chain_shape_contract_draft.md`.

- Layer 2 measures, per Chain, the plane its vertices lie in (none for a
  chain whose vertices are collinear) and the largest vertex distance from
  that plane and from the chord. Per PatchChain use it measures the side
  face of every chain edge in the use's own patch, that face's normal, and
  the tilt range between the chain's plane and those normals (0: the normal
  lies in the plane, the chain bends in depth; pi/2: the plane is the
  surface). These are raw measurements: Layer 2 names no line, curve, role
  or axis;
- the surface turn at an interior chain vertex on one side is the interior
  angle sum of that patch's faces at that vertex occurrence minus pi (the
  DD-45 data). A closed Chain is read from the use's own start vertex;
- Layer 3 PatchChainShapeRelation v0 records, per PatchChain use, each
  piece between surface corners. A surface corner is a surface turn of at
  least SURFACE_CORNER_MIN_TURN (42 degrees, between a regular 9-gon at 40
  and an 8-gon at 45; measured surface turns cluster at 0-3, 6-30 and
  80-100 degrees);
- a piece is SURFACE_LINE when every interior surface turn stays within
  GEODESIC_STRAIGHT_TOLERANCE, and SURFACE_CURVE otherwise;
- cross-check: at an interior vertex of a piece where the two adjacent
  segments span a plane, the surface turn must agree with the 3D turn
  times the sine of the tilt between that plane and the face-fan normal.
  Corner vertices are not checked: the tilt may change there. A
  disagreement above LAW_ERROR_MAX (5 degrees),
  or a vertex with no single face fan for the use, makes the piece
  UNRESOLVED with a diagnostic naming the PatchChain and the vertex.
  Neither measurement is chosen silently;
- the judgement is per PatchChain use (reaffirms DD-07 and DD-45): one
  Chain may be a surface line for one patch and a surface curve, or a
  cornered outline, for the other;
- the record itself creates, splits, merges or re-identifies no run,
  family, rail, junction, node or Layer 1 entity. It has one reader (plan
  Slice W Stage B): the per-use chord shortcut of directional runs
  (DD-30). No other Layer 3 or Layer 5 code reads it. Replacing
  single-run families by a curve record, and building a multi-segment
  surface line as one run, are later stages;
- it must not use H/V, U/V, WORLD_UP, WorldOrientation, patch types,
  Feature, API, UI or runtime semantics;
- canonical fixtures: artist arch with bevels (rim side: each arc is one
  SURFACE_LINE; front face side: the same arcs are one SURFACE_CURVE each;
  the zigzag foot chain is one SURFACE_LINE for the front face and five
  cornered pieces for the foot cap); a ring on a cone (SURFACE_CURVE with
  a tilt strictly between 0 and pi/2); capped cylinders (a 9-gon or finer
  cap rim is a curve, an 8-gon cap rim is cornered); a stepped seam (three
  pieces on both sides).

## DD-49 — RunCornerRelation v0: the corner between two run ends on one patch surface

Implemented v0 (plan Slice X; added in autonomous mode under plan decision
14). Evidence only.

- one record per pair of directional-run ends that meet at one junction
  (RunEndpointJunction) in one patch-use view at the same vertex occurrence.
  These are the pairs DD-45 considers for in-patch continuation, with one
  difference: a pair that touches a SEAM_SELF chain never continues, but it
  may form a corner;
- it stores the interior angle sum of that patch's faces at the occurrence
  (the DD-45 data) and a kind: STRAIGHT within GEODESIC_STRAIGHT_TOLERANCE
  of pi (the case that is an IN_PATCH_GEODESIC crossing), RIGHT within the
  same tolerance of pi/2 or of 3*pi/2 (a convex or a reflex right corner),
  OTHER otherwise. A pair without a single angle gets no record, and neither
  does a pair whose two ends sit on different seam sides of one vertex;
- the angle is read on the patch's own surface. Raw 3D directions, world
  axes, H/V and patch types are forbidden inputs;
- consumer: in an island without a rigid unfolded frame, Layer 5 calls two
  island lines orthogonal iff two of their runs, both in the island, are
  joined by a RIGHT corner (DD-47) or are the arriving and the leaving
  run of a bridged right corner (DD-52). A line that a conflict made
  OBLIQUE passes no axis on. The same corners orient those lines against each
  other by the corner turn law (DD-51);
- the record creates no family, crossing, rail or node;
- canonical fixtures: artist arch with bevels (a rim patch stitched to a
  foot cap across a fold: both rim arcs on one axis, the end chains on the
  other, no conflict); capped tube; an L outline with a reflex corner; a
  hexagon (every corner OTHER).

## DD-50 — Layer 4 v0: the strip feature and its constraint

Implemented v0 (plan Slice Y; added in autonomous mode under plan decision
14). Phase contract: `docs/phases/G4a_strip_feature.md`.

- Layer 4 v0 holds the feature kind STRIP (the bevel kinds of DD-54 were
  added later with the user's approval; a further kind needs the user's
  approval). A STRIP candidate is a patch with exactly
  one boundary loop made of exactly four PatchChain uses; it records, per
  use, the 3D length and whether the use is one SURFACE_LINE piece
  (DD-48). Candidates are evidence (DD-15, DD-20);
- an instance is ACCEPTED when the user option `straighten_strips` is on
  and both uses of its longer opposite pair (the larger sum of the two 3D
  lengths; on an exact tie either pair) are not one surface line on their
  own patch: curved, cornered or unresolved (DD-48). Bending in 3D is not
  read: a patch that develops without distortion (the wall of a
  cylinder) has straight long sides on its own surface however it bends
  in space, and is not a strip. Otherwise the instance is SUPPRESSED with
  a reason and stays inspectable. The shape is graded before the option:
  already a rectangle, then long sides straight on the surface, then
  option off. An instance that would be accepted on a patch laid from its
  bevel ladder (DD-54) is suppressed as laid from its bevel ladder and
  emits no STRAIGHT_STRIP. The option is off by default;
- an accepted instance emits one self-contained FeatureConstraint,
  STRAIGHT_STRIP: the patch id, the four PatchChain ids in loop order and
  the target length of each opposite pair (the mean of the two 3D lengths);
- Layer 5 reads constraints only (DD-18, DD-26) and never recognises a
  strip itself. It applies a STRAIGHT_STRIP when the patch is an island by
  itself: opposite uses lie on one axis, the runs follow the loop (+A, +B,
  -A, -B), run lengths are scaled so opposite sides are equal, and the
  existing axis solve places the nodes. A constraint whose patch shares its
  island is not applied and is reported by a diagnostic;
- a straightened strip is not isometric to its surface, so it cannot share
  a rigid unfolding. Straightening leaves a straight side straight and
  would deform a neighbour stitched along a bent side. So island assembly
  (Layer 5, reading the constraint) does not stitch a constrained patch
  when every seam its stitch gate accepts is a straight hinge: the patch
  is then an island by itself. When one of those seams is bent the patch
  stays stitched and the constraint is not applied. A seam that a user
  filter joins (DD-55) is stitched whatever this rule says: a constrained
  patch with such a seam shares its quilt, and the constraint is not
  applied (with the diagnostic above);
- the rule reads structure only: no world axis, H/V or patch types;
- Layer 4 imports Layers 0-3, never writes Layer 3 (DD-25) and never imports
  Layer 5. With both options off (`straighten_strips` and
  `straighten_bevel_strips`) every output equals a run without Layer 4;
  the second option changes nothing on a mesh that has no bevel strip
  confirmed by a mark;
- canonical fixtures: artist arch with bevels (the front face becomes a
  rectangle, the rim patches are candidates and stay suppressed as already
  rectangular); a flat annulus cut by one seam; a strip stitched across
  straight ends only (it leaves its island and is straightened; reference
  column: the flat back face between two caps); a strip stitched along a
  bent side (not applied, diagnostic).

## DD-51 — Direction conventions and the corner turn law

Implemented (plan Slice AA; added in autonomous mode under plan decision
14).

- a PatchChain use walks its boundary loop the way the faces of its patch
  wind. Where a Chain is closed (one vertex, or two occurrences of one
  source vertex at a seam) end points cannot tell the direction, and the
  use takes its orientation sign from the cyclic order of the Chain's
  edges;
- the Layer 2 vertex run and segments of a Chain follow the Chain from its
  start vertex to its end vertex, also for a Chain of one edge;
- a ChainDirectionalRun follows its Chain and a
  PatchChainDirectionalEvidence follows its use, so START and END of an
  evidence are the direction of the loop;
- the interior angle of a face corner is measured in 0..2*pi: a corner
  that turns against the face's own winding is reflex. A face whose corners
  would then sum further from (n - 2) * pi than the plain angles do (it
  crosses itself or is strongly folded) keeps the plain angles;
- corner turn law: at a RunCornerRelation of kind RIGHT (DD-49) the run
  whose role is END arrives and the run whose role is START leaves, both
  along the loop. In a layout that is not mirrored a convex corner turns
  left and a reflex corner turns right. The same holds between the
  arriving and the leaving run of a bridged right corner (DD-52), by its
  combined angle;
- consumer: Layer 5 orients the lines of an island without a rigid frame
  by this law (DD-47). The law is also a check of every solved island
  (G5a invariant 9; tests and the Tier 3 metrics);
- the law reads structure only: no world axis, H/V, patch type or raw 3D
  direction;
- canonical fixtures: artist cross band (a ring met by a seam); an
  L-shaped hexagon face; artist arch with bevels (no mirrored rim);
  reference Main_wall (a stepped outline without a frame).

## DD-52 — RunBridgedCornerRelation v0: a right corner turned over one bridge run

Implemented v0 (plan Slice AD; added in autonomous mode under plan decision
14). Evidence only.

- a directional run is straight on its patch surface, so the boundary of
  a patch turns only at corners, by pi minus the interior angle there.
  For three consecutive runs A, C, B of one loop the turn from A to B is
  the sum of the two corner turns;
- one record for an arriving run A (its END), a bridge run C and a leaving
  run B (its START), where A-C and C-B are RunCornerRelations (DD-49) of
  kind OTHER with an arriving and a leaving run, A, C and B are three
  different runs, and the combined angle theta1 + theta2 - pi is RIGHT by
  the DD-49 rule (the DD-45 tolerance; no second angle rule). It stores
  the three runs, both corner records, both angles, the combined angle
  (below pi convex, above pi reflex) and the lower of the two corners'
  confidence;
- no length is read: the bridge may be a 3 cm chamfer or a long diagonal.
  Only two consecutive corners are summed. A corner of kind RIGHT or
  STRAIGHT takes no part. A chain of OTHER corners may give overlapping
  records, each over one bridge (a notch top between two chamfers is the
  bridge of the two chamfers);
- the record is emitted whatever the island and whether or not the patch
  is planar. It sets no role and creates no family, crossing, rail, node
  or identity. Raw 3D directions, world axes, H/V and patch types are
  forbidden inputs;
- consumer: in an island without a rigid unfolded frame, Layer 5 links
  and orients the lines of A and B exactly as at a RIGHT corner (DD-47,
  DD-49, DD-51). When A and B lie on different axes with signs and C is
  OBLIQUE, C is laid by one equation per axis: its run length along A's
  direction turned by the first corner's turn, the two turns corrected
  evenly so that they add up to the exact right angle. Such an equation
  joins no nodes and is not sign-normalized; C keeps the role OBLIQUE and
  gets no stations. A corner whose B does not point where the right angle
  says lays nothing and is reported; a bridge that two records lay
  differently gets no equation and a diagnostic;
- islands with a rigid frame and strip islands do not read the record;
- like a RIGHT corner inside the DD-45 tolerance, a bridged corner whose
  turns miss the right angle by a few degrees is laid as exactly right. A
  miss larger than the island's drift shows as contradictory equations
  (UNCONSTRAINED with a diagnostic), never as silent wrong pins;
- canonical fixtures: a rectangle with one corner cut (45/45 and 30/60);
  a notch with two chamfered corners, flat and folded; reference
  Main_wall (door notches with 3 cm chamfers on a facade without a
  frame).

## DD-53 — PatchQuadLadderRelation v0: the ladder readings of a patch

Implemented v0 (plan Slice AE-1). Evidence only.

- a patch whose faces are all quads may be read as a ladder. An interior
  edge is an edge of exactly two of the patch's faces that lies on no
  Chain; a seam inside a patch (SEAM_SELF) and a non-manifold edge are
  boundary. A column is an edge-ring walk across the patch from one
  boundary edge to another over interior edges;
- a reading is a set of columns that covers every face of the patch exactly
  once, with every column open, each column side line wholly boundary or
  wholly shared with exactly one other column, and the columns forming one
  path (open: rail A, rail B and two ends) or one orientable cycle (a
  closed ring: rails only; a Moebius ring has no reading);
- a patch has zero, one or two readings (a quad grid has two: across and
  along; a single quad has two). Layer 3 keeps all of them and chooses
  none. A patch without a reading gets no record;
- a reading stores its ordered columns of faces, the faces per column, its
  rails and ends as source edges and as the PatchChain uses they lie on,
  and its profile lines: line i runs from rail A vertex i to rail B vertex
  i through the vertices across, so the two rails correspond vertex to
  vertex. A profile line of a ring cut by one seam may be a closed walk. A
  boundary use that lies on more than one side is listed as shared;
- which rail is A, which end is A and the order of the readings are fixed
  tie rules over ids (more columns first) and carry no meaning;
- the relation is pure topology: it reads Layer 0 face cycles and Layer 1
  patches, chains and uses, and no position, length, normal or direction,
  so noise and curvature cannot change it. No world axis, UV, island or
  feature;
- canonical fixtures: a 2 x 3 grid (two readings); a ring; a ring cut by
  one seam; a patch with a triangle or a five-quad pole (no reading); the
  bevel cases of `scaffold_core/tests/data/bevel_cases`.

## DD-54 — Bevel strip and bevel junction (Layer 4 kinds)

Implemented (plan Slice AE-2). Approved by the user as the second and third
feature kinds of Layer 4.

- input the user stated: a Bevel was applied; the bevel faces are bounded
  by seams and cut by seams into strips and corner junctions, so each
  strip and each junction is a patch; shapes may be curved or noisy;
- Pass 2 always builds one record per bevel patch. Layer 5 never reads
  these records; a strip confirmed by the mark may emit a constraint
  (below);
- rule A, by the source face mark (Layer 0), is authoritative wherever any
  face of the patch is marked: all MEDIUM is a BEVEL_STRIP, all WEAK a
  BEVEL_JUNCTION. MEDIUM and WEAK faces in one patch, or bevel faces
  together with STRONG or unmarked faces, give a SUPPRESSED record with a
  reason (the seams do not isolate the bevel). All STRONG is not a bevel,
  and rule B does not apply to it. A strip's direction is the one ladder
  reading (DD-53) whose rail edges have no bevel-marked face across and
  whose end edges have a bevel-marked face, the mesh border or the patch
  itself across;
- rule B, by structure, decides only patches none of whose faces is
  marked (a marked ladder patch still takes part in its state as a
  ladder, so a marked strip lets its unmarked junctions be found). Its
  records are candidates: the mark is the truth, structure is
  a suggestion, and the two sources stay apart in every record. Across a
  boundary edge lies the mesh border (no face within the model; a face
  outside the selection counts as border, as in G1), the patch itself, one
  other patch, or several faces;
  1. a reading is end-strict when every end edge borders a patch without
     a ladder relation, the mesh border or the patch itself. A ladder
     patch with exactly one end-strict reading is decided with it; with
     two it is undecided (a one-segment strip between non-quad surfaces:
     both its readings pass); with none it takes no part;
  2. an unmarked patch without a ladder relation is a junction when at
     least one of its boundary edges is an end edge of a neighbour's
     decided reading and every boundary edge lies on the mesh border, is
     such an end edge, or borders an undecided ladder patch. A rail edge
     of a decided reading, an edge on any other patch or on the patch
     itself, or a non-manifold edge breaks it;
  3. an undecided patch whose edges on junctions are end edges in exactly
     one of its readings becomes decided with that reading; when they
     point to both readings it is blocked: never decided, still counted
     as undecided in step 2. Steps 2 and 3 run in rounds over the whole
     state until a round changes nothing; a decision is never taken back,
     and the junctions are those of step 2 on the final state. The result
     does not depend on ids or order;
  4. a strip candidate is a decided patch whose decided reading has an end
     edge on a junction and whose every column has its two rail edges on
     two different other patches. A candidate with a candidate among its
     rail neighbours is dropped, judged against the candidate set before
     dropping (a bevel lies between two surfaces that are not bevels). A
     junction gets a record only when one of its edges is an end edge of
     the decided reading of a kept strip;
- under rule A a strip whose marks fit no reading or both readings is kept
  with no direction and a diagnostic names the patch: a fully triangulated
  bevel; a partial bevel whose strip ends on an unbevelled face (only the
  vertical edges of a pillar chamfered); strips whose junction faces carry
  no mark;
- a strip record keeps what later selection filters need without
  re-deriving it: the chosen reading, its rail and end uses, the neighbour
  patches on each rail, faces per column, column count, whether it is a
  ring, and a corner kind (CONVEX, CONCAVE, MIXED or UNDEFINED) taken from
  the PatchAdjacency dihedral kinds of its rail seams. That kind
  compares whole-patch normals, so beside a curved neighbour it may come
  out MIXED or UNDEFINED. A junction record keeps the strips it joins in
  the order of its boundary loop, its other neighbours and whether it
  touches the mesh border;
- the two rules read Layer 0 marks and face incidence, Layer 1, the ladder
  relation and PatchAdjacency. No position, length, world axis, UV or
  island. A world vertical enters only in the user-filter stage (DD-55),
  which reads these records;
- constraint (plan Slice AF): with the user option
  `straighten_bevel_strips` (on by default) every accepted strip by mark
  whose chosen reading is open and has no shared use emits one
  self-contained STRAIGHT_LADDER FeatureConstraint (DD-26). It carries,
  per profile line from end A to end B, the position u along the strip
  (the mean of the two rails' cumulative 3D arc lengths, so both rail
  vertices of a line share u and the strip's length is the mean of its
  rails), its rail A and rail B vertex occurrences, for the two end lines
  their inner vertices with their fraction across; the width (the mean
  3D length of the profile lines); the rail and end uses. Lengths are
  Layer 2 facts (the length of a source edge); no position is read. A
  strip by mark without a constraint gets a diagnostic with the reason
  (no reading, a closed ring, a shared use, a degenerate end line).
  Structural records never emit one;
- Layer 5 (plan Slice AF) lays a patch with that constraint from the
  constraint alone: every boundary vertex occurrence is pinned where it
  says (rail A at v = 0, rail B at v = width, line i at u_i; u is
  reversed when rail A's runs walk from end B to end A, so the strip is
  not mirrored, DD-51), rail runs on one axis and end runs on the other,
  frame kind LADDER, no stations, and it opens no ladder, bevel record or
  face. If a run end is not in the constraint the island keeps its normal
  layout with a diagnostic. When no seam of the patch is joined by a user
  filter (DD-55), the patch is an island by itself: every seam of it is
  refused ("a bevel strip is laid by itself"). When a user filter joins
  one of its seams, the patch lies in its quilt: its seams go through the
  ordinary island rules, the constraint is not applied there and no
  diagnostic says so, because that is the expected case. Its runs are
  then laid by the layout of the quilt, not by the ladder (a known
  defect: a strip whose two rails get their own lengths comes out
  sheared; plan Slice AH);
- a strip is laid with one width and parallel rails, so a strip of
  varying width is not isometric (on the user's noisy mesh single
  profile lines differ from the mean by up to 155%); interior vertices
  of a multi-segment strip are not pinned;
- known limits of rule B (the mark finds all of these): strips that meet
  at a miter without junction faces, a strip that runs to the mesh border,
  a junction that also touches a main surface, a closed ring, a
  triangulated bevel, and a bevel between non-quad main surfaces where no
  strip is decided (a cube whose main faces are triangulated: nothing is
  found). Rule B is pure topology, so it also accepts a quad band capped
  by non-quad patches that is not a bevel: the top of a free-standing
  slab with n-gon end caps, and on the building captures one single-quad
  strip with a triangle cap at a mesh border. A plain quad ladder (a
  window reveal, a wall band, any single quad) is not a kind: on an
  ordinary building half of the patches are such ladders;
- canonical fixtures: `scaffold_core/tests/data/bevel_cases` (cubes with 1
  and 3 segments, windows, arch, cylinder, noise, miters, short edge,
  triangulated; the user's rounded_wall_noise_top: 9 strips and 6
  junctions by either rule); an n-gon-capped cylinder cut into wall pieces
  (no bevel by structure).

## DD-55 — The user-filter stage and quilts

Implemented (plan Slice AH). Added with the user's authorisation to amend
G0; the wording is shown in the PR.

- the user's direction (2026-11-13): by default everything connected is
  one quilt, decided from structure. Only a user filter splits ("these are
  walls, that is a floor or a ceiling"). The user's seams always stay as
  markup: they bound patches (G1) and are never changed by Scaffold;
- quilt: a Layer 5 island is a quilt, the set of patches that lie
  together in UV as one chart. It is known as data (the stitch decisions
  of island assembly) before any unwrap;
- stage: the package `scaffold_core/user_filters/`, run once as pass 3
  (`pipeline/passes.py::run_pass_3_filters`) after pass 2 (Layer 4) and
  before Layer 5. It is a single forward pass, so DD-19 still holds. It
  reads Layers 1-4 read-only (Layer 1 patches, the Layer 2 patch normal,
  area and area_vector_length, Layer 3 PatchAdjacency, the Layer 4 bevel
  records) and writes nothing into them. It reads no Layer 0 data. Its output is a
  FilterSnapshot in `PipelineContext.filter_snapshot`: the options, one
  PatchClassRecord per patch, the SeamDirectives and diagnostics;
- options: `FilterOptions(world_up=None, horizontal_angle_degrees=45.0)`.
  With `world_up` None (the default) the stage emits nothing, and every
  output equals a run without it. `world_up` is a direction in the mesh's
  own space, the space of the Layer 0 vertex positions (Blender's
  `vertex.co`), not world space. A tool that has the Blender object turns
  a world axis into that space by the inverse of the 3x3 part of the
  object's matrix; under a rotation and a uniform scale this keeps every
  angle between a normal and the vertical. A non-uniform object scale
  changes those angles and is a stated limit. A zero `world_up` is an
  error;
- class of a patch (PatchClassRecord, with the rule that gave it): a
  patch that is not a bevel by mark is HORIZONTAL when the angle between
  its Layer 2 patch normal n and the vertical up, acos(|n . up|) in
  degrees, is at most `horizontal_angle_degrees`, and VERTICAL otherwise.
  Facing up and facing down are both HORIZONTAL. A patch has no usable
  normal when its Layer 2 normal is zero, when its Layer 2 area is zero,
  or when its Layer 2 `area_vector_length` (the length of the sum of its
  triangle area vectors) is at most 1e-3 of its Layer 2 area (the sum of
  its triangle areas): the vectors cancel, as on a closed tube. Such a
  patch is VERTICAL with the
  diagnostic FILTER_PATCH_NORMAL_DEGENERATE. The class depends only on
  the angle between a normal and the vertical, so turning the mesh and
  the vertical together changes nothing;
- bevels: only a bevel confirmed by the mark (DD-54 rule A, an ACCEPTED
  record set by the mark) takes its class by rule. Structural candidates
  (rule B) are ordinary patches here. A bevel strip is HORIZONTAL when any
  of its rail neighbours that is not a bevel by mark is HORIZONTAL, and
  VERTICAL otherwise. A strip whose record lists no such rail neighbour
  (no ladder reading, for example a triangulated strip) reads every
  adjacent patch that is not a bevel by mark the same way; with none it
  is classed by its own normal, with a diagnostic. A bevel junction takes
  the majority class of the strips by mark it joins; a tie is HORIZONTAL
  (with an INFO diagnostic); a junction that joins no strip by mark is
  classed by its own normal, with a diagnostic;
- SeamDirective: one per PatchAdjacency between two different patches
  where the filter has something to say. SPLIT when the two classes
  differ. JOIN when the two classes agree and at least one of the two
  patches is a bevel by mark. Every other seam gets no directive and is
  left to the structure. A seam inside one patch gets none;
- consumer: Layer 5 reads the stage only through SeamDirectives. It never
  reads the classes or the vertical. In island assembly a SPLIT seam is
  never stitched. A JOIN seam is stitched without the angle-defect gate
  when its two patches are in different parts of the tree; when they are
  already in one quilt it stays cut like any other seam outside the tree.
  A JOIN between two rigid parts over a rigid seam keeps the overlap gate
  (DD-47 frame, plan Slice U). Any other JOIN between two rigid parts
  cannot be checked for overlap and joins; the joined part keeps the
  larger part's frame;
- tree order: rigid seams first, then the other seams, then the JOIN
  seams. Inside the first two groups the seam with more edges comes
  first; inside the JOIN group the seam with the longer 3D length
  (PatchAdjacency.shared_length, rounded to 9 significant digits, so the
  key does not depend on the mesh's scale) comes first; then by id. The
  rounding is not a tolerance: two lengths on either side of a rounding
  step still order apart, and the lengths are only as exact as the mesh's
  float32 vertex positions. The 3D length is used because most JOIN seams have one or two
  edges, so an edge count ties them and the id would choose where a ring
  of joined patches opens. With this rule the opening is a fact of the
  mesh, not of its vertex numbering, except where several JOIN seams have
  equal 3D lengths;
- a bevel strip with a STRAIGHT_LADDER constraint and a JOIN seam lies in
  its quilt and is not laid by its ladder (DD-54);
- UV cut set: the solve states it as data. `uv_cut_chain_ids` lists every
  Chain that has a source edge walked on two sides by the patch uses
  (counted over all uses) and that no accepted stitch decision stitched:
  the seams between quilts, the seams left cut inside a quilt, every
  SEAM_SELF Chain and every slit seam inside one patch (one use that
  walks the same edges twice). A Chain whose edges are walked on one side
  only is a mesh or selection border, a cut anyway, and is not listed.
  `SolveResult.uv_cut_source_edge_ids` holds the source edges of the
  listed Chains;
- write: the G5 write boundary (`uv_transfer.py`) keeps
  `write_pinned_uvs` (pins only, no operator) and adds `write_quilt_uvs`,
  which writes the pins and runs Blender's conformal unwrap while the seam
  flag of every edge of a solved face says exactly whether the edge is in
  the UV cut set, so each quilt is one chart; it then restores the user's
  seam flags. The contract is in
  `docs/phases/G5a_skeleton_runtime.md`;
- not WorldOrientation: the vertical is a user option, lives only in this
  stage, feeds nothing into Layers 1-4 (AlignmentClass and PatchAxes do
  not see it, DD-13) and reaches Layer 5 only as SeamDirectives. A guard
  test (`scaffold_core/tests/test_forbidden_imports.py`) checks that
  Layers 0-4 do not import the stage, that the stage does not import
  Layer 5, and that no module of `core`, `constants` or a layer package
  names the vertical or the patch classes;
- policies the agent chose and the user has not decided: a junction tie
  is HORIZONTAL; a patch without a usable normal is VERTICAL; an arch
  soffit is HORIZONTAL by the angle rule and is split from its walls; the
  JOIN seams enter the tree after the other seams (the order "between the
  rigid and the other seams" was measured and gave no clear winner);
- stated limits: a ladder strip in a quilt is not laid by its ladder
  (DD-54); a quilt without a rigid frame lays only the right-corner
  component that holds its longest line, and the other components stay
  without axes; a ring of JOIN seams of equal 3D length still opens by
  id; charts are not placed or packed, so quilts may overlap each other
  in UV;
- canonical fixtures: `scaffold_core/tests/test_user_filters.py` and
  `test_layer_5_quilts.py`; the user's rounded_wall_noise_top with +Z
  (three quilts with the patch sets of the user's reference layout).

Layer 3 may derive directional evidence from final PatchChains to support
alignment, endpoint samples and ScaffoldGraph construction.

Concepts:

```text
ChainDirectionalRun:
  Direction-ready measured run derived from Chain / PatchChain geometry.

PatchChainDirectionalEvidence:
  Patch-local directional evidence derived from final PatchChain.
  It may include source edges, segment indices, direction, length, confidence
  and provenance.
```

These are evidence/views over final PatchChain. They are not competing
PatchChain identities. They are not ScaffoldEdges. They must not replace final
PatchChains as graph source of truth.

# 5. Canonical Mission Statement

Scaffold Core is an immutable B-rep-inspired interpretation pipeline for topology-aware structural UV alignment.

It builds a topology snapshot from source mesh data, attaches geometry facts, derives relation graphs with provenance, recognizes feature candidates through graph-pattern rules, resolves accepted feature instances, and runs runtime solve / UV transfer without mutating the topology snapshot.

It replaces primary H/V and WALL/FLOOR/SLOPE classifications with derived AlignmentClass and WorldOrientation layers, keeping those concepts available as runtime, debug and downstream semantics without letting them pollute the core topology model.

Feature recognition communicates with solve only through explicit FeatureConstraints.

User filters communicate with solve only through explicit SeamDirectives.

Layer 3 is frozen after Pass 1.

# 6. Open Questions

## OQ-11 — Geometry-based Chain / PatchChain refinement policy

Status: partially resolved.

Resolved:
- Final PatchChain is the public source of truth.
- Raw boundary elements are builder internals.
- Layer 3 may derive directional evidence from final PatchChains.
- Polygonal straight/turning Chains can be described by ChainDirectionalRun /
  PatchChain directional evidence.
- Directional evidence must not become a competing PatchChain identity.
- ScaffoldNode v0 may group materialized Vertex occurrences as graph-level evidence,
  but not as Layer 1 identity.
- ScaffoldNodeIncidentEdgeRelation v1 is implemented as all-pairs graph evidence
  over existing ScaffoldNode incident edge-end occurrences and must not choose
  traces, circuits, rails or continuations.
- ScaffoldContinuityComponent v0 is implemented as a continuity-family evidence
  view over existing ScaffoldEdges and incident-edge relations. It may group
  edges but must not choose traces, circuits, rails or continuation targets.
- SURFACE_SLIDING_CONTINUATION_CANDIDATE is an implemented
  ScaffoldNodeIncidentEdgeRelationKind for conservative curved/side-surface
  continuation evidence. Classifier and propagation support are implemented,
  without choosing traces, circuits, rails, UV direction or solve behavior.
- SideSurfaceContinuityEvidence v1 is implemented and refines same-side surface
  flow evidence with a direction/flow-family compatibility gate. It does not
  solve lower-side cross-patch or same-chain lower-ring flow.
- SurfaceFlowCompatibilityEvidence v0 is implemented as evidence-only
  cross-patch flow-family compatibility and must not be consumed directly by
  ScaffoldContinuityComponent.
- Connectivity-aware direction grouping is resolved by the approved DD-43
  ConnectedDirectionFamily v0 contract: direction families propagate along
  ScaffoldGraph connectivity with signed-dihedral parallel transport instead
  of global world-direction clustering.
- PatchChainShapeRelation v0 (DD-48) records, per PatchChain use, whether
  a piece is a line or a curve on its own patch surface. Since plan Slice
  W Stage B it decides the chord shortcut of a zigzag Chain per use
  (DD-30), which closes the sawtooth tuning item. The curved-chain
  policy below stays open.
