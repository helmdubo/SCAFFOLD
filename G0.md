# 0. Executive Summary

Scaffold Core is an immutable B-rep-inspired interpretation pipeline for topology-aware structural UV alignment.

It does not attempt to become a CAD kernel. It borrows B-rep discipline — topology/geometry separation, oriented edge-use, shells, loops, adjacency graphs, feature recognition — and applies it to a polygonal Blender mesh workflow.

Scaffold Core builds a read-only **Topology Snapshot** from a source mesh, attaches derived **Geometry Facts**, derives **Relation Graphs** such as adjacency, alignment, continuation and world semantics, recognizes higher-level **Feature Candidates**, resolves them into **Feature Instances**, and runs **Runtime/Solve** steps such as skeleton solve, pin policy and UV transfer.

Scaffold owns interpretation.  
Blender owns mesh editing.

Recommended Blender add-on metadata:

```python
bl_info = {
    "name": "Scaffold",
    "author": "...",
    "version": (0, 1, 0),
    "blender": (4, 0, 0),
    "category": "UV",
    "description": "Structural UV for architectural meshes",
    "location": "UV Editor > Sidebar > Scaffold",
}
```

`category = "UV"` is intentional. The primary workflow lives in UV space.

The core package is:

```text
scaffold_core/
```

The add-on wrapper may later live in:

```text
scaffold/
```

# 1. Core Design Goal

Remove old hard-coded assumptions:

```text
old:
  WALL / FLOOR / SLOPE as primary patch types
  H_FRAME / V_FRAME as primary chain roles
  local patch basis as early truth
  solve logic mixed with recognition logic
  ContinuationEdge ad-hoc alongside Chain

new:
  geometry facts are raw, uninterpreted
  topology is explicit, oriented, immutable
  PatchChain is the final patch-local boundary edge source of truth
  AlignmentClass derives axis-like structure from PatchChain directional evidence
  WorldOrientation is a parallel semantic overlay
  features are graph-pattern interpretations with evidence
  runtime roles are late, derived, and task-specific
  continuation is a first-class Layer 3 relation
```

Two architectural cycles are explicitly forbidden:

```text
forbidden:
  skeleton solve → determines axes
  world orientation → determines alignment
```

Instead:

```text
Layer 2:
  raw geometry directions

Layer 3:
  AlignmentClass and PatchAxes are derived before solve

Layer 5:
  skeleton solve consumes AlignmentClass / PatchAxes and computes coordinates
```

And:

```text
WorldOrientation is a deferred parallel semantic overlay.
WorldOrientation does not depend on skeleton solve.
AlignmentClass and PatchAxes must not use WORLD_UP or WorldOrientation labels.
WorldOrientation must not feed back into Layer 1 topology, PatchChain identity,
AlignmentClass grouping or PatchAxes selection.
```

# 2. Layer Overview

```text
Layer 0 — Source Mesh Snapshot
Layer 1 — Immutable Topology Snapshot
Layer 2 — Geometry Facts
Layer 3 — Derived Relations
Layer 4 — Feature Grammar
Layer 5 — Runtime / Solve
```

Layer 3 is frozen after Pass 1. Layer 4 communicates with Layer 5 only through explicit `FeatureConstraint` objects.

# 3. G1 Patch Segmentation and Shell Policy

G1 patch segmentation uses selected-face flood fill.

A source edge blocks Patch flood fill and becomes a Patch boundary if:

```text
- it is a mesh/selection border;
- it is non-manifold in selected scope;
- it has an explicit Scaffold boundary mark;
- it has a Blender UV Seam.
```

Blender Sharp is **not** a default Patch boundary source in G1.

A future optional command/flag may support:

```text
make seams by sharps
```

That future option should convert sharp information into seam/boundary input before segmentation. It must not make Sharp a hidden default segmentation source.

Material boundaries, normal-angle thresholds and existing UV island boundaries are also not default G1 segmentation sources.

G1 shell detection uses edge-connected components of selected faces.

Shell connectivity ignores Patch segmentation boundaries: seams and explicit boundary marks can split Patches but do not split Shells.

Vertex-only contact does not connect Shells.

Non-manifold edge connectivity keeps faces in the same Shell candidate, but emits a degraded non-manifold diagnostic.

Layer 1 boundary construction follows this intended pipeline:

```text
1. Flood fill selected faces until boundary edges.
2. Build Patch boundaries and raw boundary cycles.
3. For every boundary edge, classify neighbor context:
   - self patch neighbor / seam-self;
   - other patch neighbor;
   - no patch neighbor / open boundary;
   - non-manifold.
4. Build draft boundary runs internally.
5. Redefine/coalesce/split draft runs according to policy.
6. Materialize final BoundaryLoop with final PatchChains.
7. Downstream systems use final PatchChains.
```

Final PatchChain may be the same as the draft run, or may be split/coalesced.
Do not introduce an extra public span or effective-chain source-of-truth layer.
If helper spans/runs are needed during construction, they stay private/internal.

Canonical cylinder sanity check:

```text
Cylinder tube without caps + one seam cut:
  Patch count: 1
  BoundaryLoop count: 1 OUTER
  Chain count: 3
  PatchChain count: 4
  LoopCorner count: 4
  ScaffoldNode count: 2
  ScaffoldEdge count: 4
  SELF_SEAM ScaffoldJunction count: 2

PatchChains:
  1. seam side A
  2. cap/border ring A
  3. seam side B
  4. cap/border ring B

LocalFaceFanGeometryFacts:
  many, not 2
  local normal evidence, not scaffold graph nodes

ScaffoldNode:
  graph-level evidence node assembled from loop corners and endpoint evidence;
  seam-side materialized Vertex occurrences may group by SourceVertexId.

ScaffoldJunction:
  ordinary ScaffoldNodes remain unclassified unless a ScaffoldJunction
  classifier emits a record. SELF_SEAM classifies the 2 seam endpoint
  ScaffoldNodes in this fixture after ScaffoldGraph construction.

Future ScaffoldCircuit:
  likely 2 cap/border circuits
```

# 4. Design Decisions Register

## DD-01 — Topology is immutable snapshot
Scaffold Core does not mutate topology in place.

## DD-02 — PatchChain is mandatory
All oriented boundary use is represented through PatchChain.

## DD-03 — Topology and geometry are separate
Layer 1 stores incidence/orientation. Layer 2 stores measured geometry.

## DD-04 — H/V is not a primary stored role
H/V-like labels are derived runtime/debug labels.

## DD-05 — WALL/FLOOR/SLOPE is not a primary patch type
World-facing semantics are derived WorldOrientation facts.

## DD-06 — Relations are derived caches with provenance
Relations store confidence, evidence, source and snapshot context.

## DD-07 — Alignment membership is per PatchChain
A Chain may have multiple PatchChains with different AlignmentClass memberships.

## DD-08 — Patch axes are derived from AlignmentClasses
PatchAxes is Layer 3 classification, not solve output.

## DD-09 — Continuation is a Layer 3 relation
Old ContinuationEdge becomes ChainContinuationRelation.

## DD-10 — Dihedral is a PatchAdjacency relation
Signed dihedral references patch pair, shared Chain and both PatchChains.

## DD-11 — WorldOrientation is a derived relation namespace
SurfaceRole, WorldEdgeKind and WorldCornerKind are derived semantics.

## DD-12 — Base WorldOrientation does not depend on Runtime/Solve
Solve output must not redefine world semantics.

## DD-13 — Alignment and PatchAxes do not use WorldOrientation
AlignmentClass and PatchAxes consume patch-local directional evidence only.
They must not use WORLD_UP vector bias, SurfaceRole labels or WorldOrientation
labels.

## DD-14 — Runtime solve consumes lower layers only
Runtime solve must not discover or mutate topology, geometry or base relations.

## DD-15 — Feature recognition returns candidates, not decisions
Rules produce FeatureCandidates. Resolver produces FeatureInstances.

## DD-16 — Full rebuild is preferred in v1
Correctness and debuggability beat incremental complexity.

## DD-17 — User overrides are inputs, not topology mutations
Overrides affect rebuild interpretation.

## DD-18 — Skeleton solve supports optional FeatureConstraints
FeatureConstraints are the Layer 4 → Layer 5 bridge.

## DD-19 — Two-pass maximum in v1
No iterative feature/solve convergence loop.

## DD-20 — Suppressed candidates are retained
Suppressed/rejected/weak candidates are inspectable diagnostics.

## DD-21 — Detail generation is external
Detail/decal/wear systems consume Scaffold APIs.

## DD-22 — SEAM_SELF is first-class
Two PatchChains of one Chain in one Patch is supported.

## DD-23 — Architecture allows N AlignmentClasses per patch; v1 resolves at most two
Non-orthogonal/curved/N-family cases are future work.

## DD-24 — Direction clustering is conservative in v1
Straight-like PatchChains only, chord direction only, fixed tolerance.

## DD-25 — Layer 3 is frozen after Pass 1
Pass 2 may consume Layer 3 but must not write to it.

## DD-26 — FeatureConstraint is first-class
FeatureConstraint is the only channel from accepted features into solve.

## DD-29 — Chain coalescing is staged

Layer 1 materializes final PatchChains from raw boundary elements.

Raw boundary sides, atomic source edges, draft boundary runs and raw boundary
cycles are builder internals. They are not public model entities.

Boundary coalescing uses topology/materialization context only:
- boundary run kind;
- Patch context;
- seam/cut side;
- neighbour context;
- loop materialization.

Border runs may coalesce into ordered Chains when materialization policy
identifies them as one final PatchChain.

Reason:
Cylinder tube without caps + one seam cut showed that edge-atomic border Chains
prevent correct materialized BoundaryLoop construction. Border ring runs must
be allowed to coalesce into final PatchChains.

Geometry may later describe or classify a final PatchChain, but it must not
create a competing public PatchChain identity.

## DD-30 — Chain refinement does not change Layer 1 Chain identity

Layer 1 Chain identity is decided by topology coalescing only.

Geometry-driven Chain refinement, when introduced, lives in Layer 3 and
must be computed before AlignmentClass consumes Chain-like entities.

Refinement may produce derived sub-chain entities or alignment-level
groupings that AlignmentClass consumes. It must not rewrite, split, or
re-id existing Layer 1 Chain records after Pass 0.

This preserves stable Chain ids for downstream references and keeps
geometry-driven decisions inside Layer 3.

Directional runs are chosen per PatchChain use (plan Slice W Stage B,
user-approved 2026-11-13). A zigzag Chain keeps its single chord-directed
run only for a use where the whole Chain is one SURFACE_LINE piece on that
use's side (DD-48); every other use gets the runs split at direction
changes. The two uses of one Chain may therefore carry different runs. A
Chain whose split is a single run, and a monotone-turning arc, are not
affected.

## DD-31 — PatchChain endpoint relations are local and axis-free

PatchChain endpoint relations are Layer 3 derived relations between
patch-local `PatchChainDirectionalEvidence` endpoint samples at the same
Vertex. They classify local structural relations such as continuation
candidate, corner connector, oblique connector, ambiguous and degenerate.
They must not use U/V labels, H/V labels, WORLD_UP, WorldOrientation labels
or runtime solve output.

## DD-32 — Surface normals for PatchChain are derived facts, not Layer 1 topology

Layer 1 `PatchChain` must not store face normals or averaged normals. Owner
normals for endpoint relations are derived from Layer 2 geometry or Layer 3
evidence. `LocalFaceFanGeometryFacts` may provide local endpoint normals.

## DD-33 — ScaffoldGraph is derived from endpoint relations and LoopCorners

ScaffoldGraph is a Layer 3 derived structure built from
`PatchChainEndpointRelation`, `LoopCorner` and implemented `ScaffoldNode` evidence,
not from raw Chain or world axes. ScaffoldTrace and ScaffoldRail (DD-46,
DD-47) are separate ordered evidence views over direction families and
run-endpoint junctions; they do not change this graph. `ScaffoldEdge`
is a graph-level view of final PatchChain, not a competing PatchChain identity.

## DD-34 — Final PatchChain is the single source of truth

BoundaryLoop contains final PatchChains. Raw boundary sides, atomic source
edges and draft runs are builder internals. ScaffoldGraph must use final
PatchChains as graph edges, not a parallel effective PatchChain layer.

## DD-35 — LoopCorner is patch-local; ScaffoldJunction is graph-level

LoopCorner is the local transition between adjacent PatchChains inside one
BoundaryLoop. A LoopCorner may feed ScaffoldNode evidence. It becomes a
ScaffoldJunction only when a graph-level classifier assigns a
ScaffoldJunctionKind to an existing ScaffoldNode. ScaffoldJunction is a
classification overlay, not a separate graph node identity.

Implemented ScaffoldJunctionKind vocabulary includes:
- SELF_SEAM: two incident final PatchChains share the same ChainId and same
  PatchId, representing the supported SEAM_SELF case.
- CROSS_PATCH: an existing ScaffoldNode's incident final ScaffoldEdges
  reference more than one distinct PatchId.

Future ScaffoldJunctionKind vocabulary beyond SELF_SEAM/CROSS_PATCH includes:
- BRANCH;
- TERMINUS or BORDER_TERMINUS;
- AMBIGUOUS or DEGRADED when describing evidence quality.

Ordinary ScaffoldNodes remain unclassified unless a ScaffoldJunction classifier
emits a record.

## DD-36 — LocalFaceFan is geometry evidence, not graph topology

LocalFaceFanGeometryFacts provides local normals for endpoint evidence. It is
not a ScaffoldNode and not a graph entity.

## DD-37 — Seam cuts may materialize duplicate topology Vertex occurrences

A seam cut may materialize multiple topology Vertex occurrences for one source
vertex.

One source vertex can appear on different sides of a materialized BoundaryLoop
or seam cut. These occurrences may receive distinct topology VertexIds while
retaining provenance to the same source vertex.

Reason:
Materialized UV-cut topology needs separate loop-side occurrences for the same
source vertex. This is required for correct BoundaryLoop traversal, PatchChain
construction, LoopCorner construction and ScaffoldNode grouping.

Implications:
- VertexId equality is topology-occurrence equality, not source-vertex equality.
- SourceVertexId equality is provenance equality.
- Public queries that need source-space grouping must explicitly group by
  SourceVertexId or structural provenance.
- ScaffoldNode construction may aggregate multiple materialized Vertex
  occurrences into one graph node.

## DD-38 — ScaffoldNode v0 is graph-level evidence, not Layer 1 identity

ScaffoldNode v0 is a Layer 3 derived relation record assembled from LoopCorner,
PatchChainEndpointSample and PatchChainEndpointRelation evidence.

Grouping policy v0:
- group materialized topology Vertex occurrences by SourceVertexId when provenance exists;
- fall back to topology VertexId grouping when no SourceVertexId provenance exists;
- retain evidence ids, incident PatchChain ids, Patch ids, confidence and provenance.

ScaffoldNode does not mutate, merge, split or replace Layer 1 Vertex, Chain,
PatchChain or BoundaryLoop identity. It does not classify ScaffoldJunctions and
does not build ScaffoldTraces, ScaffoldCircuits or ScaffoldRails.
ScaffoldJunction classification must not change ScaffoldNode grouping, change
PatchChain identity, walk traces, detect circuits, select rails, choose
continuations or introduce UV, runtime or feature semantics.

## DD-39 - ScaffoldNodeIncidentEdgeRelation v1 is all-pairs evidence

Implemented ScaffoldNodeIncidentEdgeRelation v1 is a complete unordered all-pairs
Layer 3 relation over incident ScaffoldEdge endpoint occurrences at one
existing ScaffoldNode. For n incident edge-end occurrences at one ScaffoldNode,
v1 emits C(n,2) relations.

Emission is graph-structural. Missing PatchChainEndpointSample or
PatchChainEndpointRelation evidence must not cause an edge-end pair to
disappear. When endpoint evidence is missing, the pair remains present and is
classified with missing or degraded evidence quality.

Classification is evidence-backed. It may use tangent direction evidence,
owner normal evidence, direction_dot, normal_dot, endpoint sample ids,
PatchChainEndpointRelation id when available, confidence and evidence quality.
It is evidence only. It must not select trace paths, circuits, rails,
continuations, UV behavior or runtime behavior.

Implemented v1 relation kinds:
- STRAIGHT_CONTINUATION_CANDIDATE: opposite tangent/chord evidence;
  compatible owner-normal proof may be absent or weak.
- SURFACE_CONTINUATION_CANDIDATE: continuation candidate with compatible owner
  normals for opposite-tangent or straight-ish surface continuation.
- CROSS_SURFACE_CONNECTOR: tangent may align or connect, but owner normals
  diverge strongly.
- ORTHOGONAL_CORNER: tangent evidence is orthogonal.
- OBLIQUE_CONNECTOR: tangent evidence is neither collinear nor orthogonal.
- SAME_RAY_AMBIGUOUS: endpoint tangents point in the same ray direction away
  from the node.
- MISSING_ENDPOINT_EVIDENCE: the edge-end pair exists but endpoint
  sample/relation evidence is absent.
- DEGRADED: tangent, normal, confidence or evidence is zero, unknown or
  collapsed.

Implemented relation kind:
- SURFACE_SLIDING_CONTINUATION_CANDIDATE: node-local relation between two
  existing ScaffoldEdge endpoint occurrences whose local tangent/chord
  classification may otherwise look orthogonal or same-ray, but explicit
  same-side-surface evidence plus compatible local owner normals support
  continuation along the same curved or side surface. It is not a trace path
  choice, not a selected next edge, not a rail/circuit decision and not a UV
  direction.

SURFACE_SLIDING_CONTINUATION_CANDIDATE requires local owner-normal evidence,
compatible local owner normals and explicit same-side-surface evidence.
Current SideSurfaceContinuityEvidence v1 is consumed as this explicit
same-side-surface evidence source and includes the direction/flow-family
compatibility gate before this evidence may promote a pair to
SURFACE_SLIDING_CONTINUATION_CANDIDATE. Same patch, same loop,
END -> START adjacency and compatible local normals are not sufficient by
themselves under v1. Missing, degraded or direction-family-incompatible evidence
must not produce this kind under v1.
SharedChainPatchChainRelation alone must not produce this kind. Cross-patch
cap, corner and shared-boundary cases must remain non-propagating unless
same-side-surface and direction/flow-family evidence is explicit and safe.

ScaffoldNodeIncidentEdgeRelation v1 must not change ScaffoldNode grouping,
ScaffoldEdge identity, PatchChain identity, Chain identity, Vertex identity or
BoundaryLoop identity. It must not use H/V, U/V, WORLD_UP, WorldOrientation,

## DD-43 — ConnectedDirectionFamily v0 is connectivity-propagated direction-family evidence

Approved ConnectedDirectionFamily v0 is a Layer 3 derived evidence view over
PatchChainDirectionalEvidence and ScaffoldGraph connectivity. It groups
directional evidence into direction families by propagation along topology,
not by world-direction comparison.

Seeds and propagation:
- seeds are non-degenerate PatchChainDirectionalEvidence records;
- membership propagates only along ScaffoldGraph connectivity
  (ScaffoldNode incidence and SharedChainPatchChainRelation);
- evidence in disconnected Shells must never share a family
  (canonical negative: detached_parallel_walls);
- cross-patch transport rotates the carried direction around the shared
  chain by the signed dihedral (parallel transport). Dihedral modulates
  HOW a direction transports, never WHETHER it transports: there is no
  dihedral threshold; user seams already encode cut intent;
- SHARED_CHAIN crossings transport only across a straight hinge: both
  PatchChains of the shared Chain carry exactly one directional run. A
  curved multi-run Chain has no single rotation axis and does not
  transport;
- a family visits each patch at most once as one continuous in-patch
  segment. In-patch geodesic crossings form segments first, SHARED_CHAIN
  merges precede node merges, and a merge that would put two separate
  segments of one patch into one family is blocked. Opposite sides of a
  patch never share a family;
- a node crossing records the hinge Chain that passes through its node;
  two patches may share several Chains;
- a node crossing never folds back: after transport about its hinge, the
  two runs leave the node in opposite directions. Runs that leave it the
  same way (a patch wrapping around a corner node) do not cross. The run
  end at the node is the end on the node vertex.

Transport gates must distinguish junction geometry, consistent with the
two-seam-tube / tube-with-cap fixture pair:
- same-chain crossings (seam flow, cap rims) cross a locally flat
  junction: diverging owner normals disprove the flow;
- different-chain node crossings (ring flow around curved surfaces)
  legitimately have diverging owner normals and must not be
  normal-gated; they gate on transported-direction compatibility and
  non-degraded endpoint evidence.

Canonical fixture expectations:
- detached_parallel_walls: the two walls never share a family;
- l_corridor_tunnel_seamed_folds: one width (profile) family across floor,
  wall and ceiling; one length rail per fold line (floor+wall,
  wall+ceiling);
- beveled_wall_corner: one horizontal family across wall A, chamfer and
  wall B; one vertical rail per fold line (wall A+chamfer, chamfer+wall
  B);
- tube_with_cap: cap and side families stay separate;
- cylinder_tube two-seam variant: top ring family and bottom ring family
  across both side patches;
- reflex_corner (a wall hinged into the notch of an L-shaped wall): its
  bottom and the notch bottom stay separate families; the two tops share
  one family.

Non-goals and restrictions:
- v0 is evidence only: it must not choose traces, rails, circuits,
  continuations, UV direction or solve behavior;
- v0 must not change ScaffoldContinuityComponent propagation,
  ScaffoldNode/ScaffoldEdge identity or any Layer 1 identity;
- it must not use H/V, U/V, WORLD_UP, WorldOrientation, Feature, API,
  UI or runtime semantics;
- AlignmentClass remains in place; existing consumers stay on
  AlignmentClass until a later approved slice migrates them. New
  consumers should prefer ConnectedDirectionFamily.

## DD-47 — ScaffoldRail v1 is a direction-stable ScaffoldTrace

Implemented ScaffoldRail v1 is a ScaffoldTrace whose station order carries a
transported orientation sign per member (+1 along the rail, -1 against it, 0
unknown), suitable for consumption as a conditional axis by Layer 5.

- it carries ordered members and stations (in a consumable rail station i is
  the step between trace nodes i and i + 1; a branched or looped rail lists
  its stations by station id), ordered trace nodes, first and last trace
  node, a closed-loop flag (the stations form one cycle), signs, crossing
  records, branch records, loop ambiguity records, confidence and
  diagnostics;
- signs come from the trace nodes of the links before and after each station;
  a rail of one station orients its uses against its first member. They are
  never taken from world direction comparison or a runtime greedy walk;
- a rail is consumable by Layer 5 only when it has more than one member, no
  branch record, no closed loop, no diagnostics and a nonzero sign on every
  member;
- loops: a closed loop is not a linear rail. It opens only where a
  structural cut the rail builder does not own (the seams an island leaves
  cut, a split seam) already opens it; the rail builder never picks a
  start;
- branches: a station with more than two links, or a trace node touched by
  more than two stations, is a branch record; a path that comes back to a
  node it passed is not a line. Branches stay explicit until a Layer 4
  feature rule or an approved Layer 3 continuation contract resolves them;
- cut view: a consumer that owns a structural cut (the members it keeps and
  the hinge Chains its cut keeps joined, for example one island's runs and
  stitched seams) may ask Layer 3 to cut a family's rail. A crossing survives
  when both members are kept and it stays inside one patch or passes a kept
  Chain; each connected piece is ordered through its stations like a whole
  rail and names its stations. A loop opens exactly where the cut opens it;
  a branch, or a loop the cut leaves closed, stays unordered with a
  diagnostic. The cut view is computed on demand and is not stored in
  RelationSnapshot;
- consumer rule: Layer 5 consumes rails through the cut view of each island
  and may check them against its own island lines and frame as validation
  outputs. It must not reconstruct missing or ambiguous rail order, loop
  signs or branch choices by local BFS, greedy traversal, lexical ordering,
  world-direction comparison or ad-hoc sign propagation; it diagnoses and
  degrades instead;
- Layer 5 takes its island lines from the cut view. An island without a
  rigid unfolded frame takes its in-line run signs from its ordered
  island rails; a run on an unordered island rail stays unsigned with a
  diagnostic and adds no length equation, but keeps its axis role. Order
  and signs inside a rail come only from the rails; the axis bipartition
  of such an island and the relative orientation of different rails
  (which flips whole lines, never one run) stay with Layer 5. Both read
  RunCornerRelation RIGHT corners (DD-49): the bipartition takes
  orthogonality from them, the orientation follows the corner turn law
  (DD-51). Neither compares raw 3D directions. A line that two corners
  orient differently loses its signs with a diagnostic; a signed axis line
  that the corners do not tie to the island's longest line keeps its rail
  signs and is reported;
- canonical fixtures: two-seam cylinder tube (both rim rings stay closed
  loop rails; the island cut opens each at the seam the island leaves cut);
  artist multiseam cylinder (both rims open into ordered island rails);
  l_corridor_tunnel_seamed_folds (open consumable length rails);
  beveled_wall_corner and t_vertex_wall (the two uses of a hinge are one
  station); extruded_cross (top and bottom rims are distinct rails);
  tube_with_cap (cap and side rails stay separate); t_vertex_wall with its
  right hinge cut (a branch at w1);
- ScaffoldRail remains Layer 3 evidence: it must not choose UV coordinates,
  pins, island packing, texel scale, feature constraints or Blender
  operations.

## DD-48 — PatchChain shape is judged per use on its own patch surface

Implemented v0 (plan Slice W, Stages A and B). Background, stages and
measurements: `docs/architecture/chain_shape_contract_draft.md`.

- Layer 2 measures, per Chain, the plane its vertices lie in (none for a
  chain whose vertices are collinear) and the largest vertex distance from
  that plane and from the chord. Per PatchChain use it measures the side
  face of every chain edge in the use's own patch, that face's normal, and
  the tilt range between the chain's plane and those normals (0: the normal
  lies in the plane, the chain bends in depth; pi/2: the plane is the
  surface). These are raw measurements: Layer 2 names no line, curve, role
  or axis;
- the surface turn at an interior chain vertex on one side is the interior
  angle sum of that patch's faces at that vertex occurrence minus pi (the
  DD-45 data). A closed Chain is read from the use's own start vertex;
- Layer 3 PatchChainShapeRelation v0 records, per PatchChain use, each
  piece between surface corners. A surface corner is a surface turn of at
  least SURFACE_CORNER_MIN_TURN (42 degrees, between a regular 9-gon at 40
  and an 8-gon at 45; measured surface turns cluster at 0-3, 6-30 and
  80-100 degrees);
- a piece is SURFACE_LINE when every interior surface turn stays within
  GEODESIC_STRAIGHT_TOLERANCE, and SURFACE_CURVE otherwise;
- cross-check: at an interior vertex of a piece where the two adjacent
  segments span a plane, the surface turn must agree with the 3D turn
  times the sine of the tilt between that plane and the face-fan normal.
  Corner vertices are not checked: the tilt may change there. A
  disagreement above LAW_ERROR_MAX (5 degrees),
  or a vertex with no single face fan for the use, makes the piece
  UNRESOLVED with a diagnostic naming the PatchChain and the vertex.
  Neither measurement is chosen silently;
- the judgement is per PatchChain use (reaffirms DD-07 and DD-45): one
  Chain may be a surface line for one patch and a surface curve, or a
  cornered outline, for the other;
- the record itself creates, splits, merges or re-identifies no run,
  family, rail, junction, node or Layer 1 entity. It has one reader (plan
  Slice W Stage B): the per-use chord shortcut of directional runs
  (DD-30). No other Layer 3 or Layer 5 code reads it. Replacing
  single-run families by a curve record, and building a multi-segment
  surface line as one run, are later stages;
- it must not use H/V, U/V, WORLD_UP, WorldOrientation, patch types,
  Feature, API, UI or runtime semantics;
- canonical fixtures: artist arch with bevels (rim side: each arc is one
  SURFACE_LINE; front face side: the same arcs are one SURFACE_CURVE each;
  the zigzag foot chain is one SURFACE_LINE for the front face and five
  cornered pieces for the foot cap); a ring on a cone (SURFACE_CURVE with
  a tilt strictly between 0 and pi/2); capped cylinders (a 9-gon or finer
  cap rim is a curve, an 8-gon cap rim is cornered); a stepped seam (three
  pieces on both sides).

## DD-49 — RunCornerRelation v0: the corner between two run ends on one patch surface

Implemented v0 (plan Slice X; added in autonomous mode under plan decision

## DD-50 — Layer 4 v0: the strip feature and its constraint

Implemented v0 (plan Slice Y; added in autonomous mode under plan decision
14). Phase contract: `docs/phases/G4a_strip_feature.md`.

- Layer 4 holds one feature kind, STRIP. A candidate is a patch with exactly
  one boundary loop made of exactly four PatchChain uses; it records, per
  use, the 3D length, whether the Chain is bent in 3D and whether the use is
  one SURFACE_LINE piece (DD-48). Candidates are evidence (DD-15, DD-20);
- an instance is ACCEPTED when the user option `straighten_strips` is on,
  the strip needs straightening (some use is not one surface line, or two
  opposite uses differ in length by more than 1%), and at least one opposite
  pair has both uses bent. Otherwise it is SUPPRESSED with a reason and
  stays inspectable. The option is off by default;
- an accepted instance emits one self-contained FeatureConstraint,
  STRAIGHT_STRIP: the patch id, the four PatchChain ids in loop order and
  the target length of each opposite pair (the mean of the two 3D lengths);
- Layer 5 reads constraints only (DD-18, DD-26) and never recognises a
  strip itself. It applies a STRAIGHT_STRIP when the patch is an island by
  itself: opposite uses lie on one axis, the runs follow the loop (+A, +B,
  -A, -B), run lengths are scaled so opposite sides are equal, and the
  existing axis solve places the nodes. A constraint whose patch shares its
  island is not applied and is reported by a diagnostic;
- a straightened strip is not isometric to its surface, so it cannot share
  a rigid unfolding. Straightening leaves a straight side straight and
  would deform a neighbour stitched along a bent side. So island assembly
  (Layer 5, reading the constraint) does not stitch a constrained patch
  when every seam its stitch gate accepts is a straight hinge: the patch
  is then an island by itself. When one of those seams is bent the patch
  stays stitched and the constraint is not applied;
- the rule reads structure only: no world axis, H/V or patch types;
- Layer 4 imports Layers 0-3, never writes Layer 3 (DD-25) and never imports
  Layer 5. With the option off every output equals a run without Layer 4;
- canonical fixtures: artist arch with bevels (the front face becomes a
  rectangle, the rim patches are candidates and stay suppressed as already
  rectangular); a flat annulus cut by one seam; a strip stitched across
  straight ends only (it leaves its island and is straightened; reference
  column: the flat back face between two caps); a strip stitched along a
  bent side (not applied, diagnostic).

## DD-51 — Direction conventions and the corner turn law

Implemented (plan Slice AA; added in autonomous mode under plan decision
14).

- a PatchChain use walks its boundary loop the way the faces of its patch
  wind. Where a Chain is closed (one vertex, or two occurrences of one
  source vertex at a seam) end points cannot tell the direction, and the
  use takes its orientation sign from the cyclic order of the Chain's
  edges;
- the Layer 2 vertex run and segments of a Chain follow the Chain from its
  start vertex to its end vertex, also for a Chain of one edge;
- a ChainDirectionalRun follows its Chain and a
  PatchChainDirectionalEvidence follows its use, so START and END of an
  evidence are the direction of the loop;
- the interior angle of a face corner is measured in 0..2*pi: a corner
  that turns against the face's own winding is reflex. A face whose corners
  would then sum further from (n - 2) * pi than the plain angles do (it
  crosses itself or is strongly folded) keeps the plain angles;
- corner turn law: at a RunCornerRelation of kind RIGHT (DD-49) the run
  whose role is END arrives and the run whose role is START leaves, both
  along the loop. In a layout that is not mirrored a convex corner turns
  left and a reflex corner turns right;
- consumer: Layer 5 orients the lines of an island without a rigid frame
  by this law (DD-47). The law is also a check of every solved island
  (G5a invariant 9; tests and the Tier 3 metrics);
- the law reads structure only: no world axis, H/V, patch type or raw 3D
  direction;
- canonical fixtures: artist cross band (a ring met by a seam); an
  L-shaped hexagon face; artist arch with bevels (no mirrored rim);
  reference Main_wall (a stepped outline without a frame).

# 5. Canonical Mission Statement

Scaffold Core is an immutable B-rep-inspired interpretation pipeline for topology-aware structural UV alignment.

It builds a topology snapshot from source mesh data, attaches geometry facts, derives relation graphs with provenance, recognizes feature candidates through graph-pattern rules, resolves accepted feature instances, and runs runtime solve / UV transfer without mutating the topology snapshot.

It replaces primary H/V and WALL/FLOOR/SLOPE classifications with derived AlignmentClass and WorldOrientation layers, keeping those concepts available as runtime, debug and downstream semantics without letting them pollute the core topology model.

Feature recognition communicates with solve only through explicit FeatureConstraints.

Layer 3 is frozen after Pass 1.
